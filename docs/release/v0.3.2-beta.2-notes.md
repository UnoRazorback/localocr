## What changed since build 10

### Amounts that ended in stray letters are finished

Apple Vision often reads an amount correctly up to its cents and then returns
made-up accented letters in place of the last digits (`25,740.0ął` for
`25,740.00`). Build 11 looks again at just that line, cut out of the page and
enlarged, and finishes the amount. Every character the first reading saw is
kept; only the missing digits are taken, and only when the second look is a
clean amount that begins with exactly the digits already read. Otherwise the
line is left as recognized. Text such as `0.25µm` is not touched, and rotated
pages are not repaired.

Measured on 112 pages from 16 real construction documents (300 DPI): amounts
read exactly rose from 91.9% to 95.1%, words from 97.5% to 98.3%, and garbled
amounts fell from 134 to 6, with no new wrong amounts. On 291 pages from 80
scanned PDFs, garbled amounts fell from 183 to 18. Method and limits are in
[the benchmark notes](../../benchmarks/README.md). OCR can still be wrong;
check amounts against the source page.

### A read can no longer wait forever

On some near-blank scanned pages Apple Vision occasionally stops answering a
request. Build 10 and earlier then waited indefinitely. Build 11 gives up on
a request after 90 seconds, lists the page in `failed_pages` with the message
"Apple Vision stopped answering in this process", and fails later recognition
in that process at once. Nothing is wrong with the file: run the operation
again, after quitting and reopening LocalOCR Studio or the MCP client if one
is open. In testing this affected a few launches in a hundred on one
affected page; ordinary text pages never showed it.

### Optional amount check

`ocr_pdf` and `ocr_pdf_batch` accept `verify_amounts`, and `localocr ocr` and
`localocr batch` accept `--verify-amounts`. Recognized pages with amounts are
read a second time at another resolution, and an amount the second read does
not repeat is marked in the page text
(`6,435.00 [not confirmed by second read]`). The result gains `amount_check`.
It is off by default and takes about twice as long.

This is a second opinion, not a guarantee. On the benchmark pages it marked
1.9% of correct amounts and none of the 10 amounts that were misread as a
different clean amount, because the second read made the same mistake. An
unmarked amount is not proven right.

### Tool descriptions

The MCP descriptions of `inspect_pdf`, `ocr_pdf`, `ocr_image` and `force_ocr`
now say what the tools return: sparse-text scans are read, table-row cells
are joined with ` | `, and `force_ocr` should normally be left off.

### After installing

The OCR cache version changed, so pages recognized by earlier builds are read
again the first time. As with earlier builds, the first recognition from a
newly installed build can take up to a minute; process one document and
discard the result before relying on output from a new install.
